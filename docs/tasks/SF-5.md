# SF-5 — auth-service: NestJS gRPC microservice

## Чек-лист (acceptance criteria)

- [x] gRPC-сервер стартует на порту 5001
- [x] `ValidateToken` RPC валидирует JWT и возвращает данные юзера
- [x] `register` создаёт юзера с хешированным паролем
- [x] `login` возвращает access + refresh токены
- [x] `user.registered` Kafka-событие публикуется при регистрации
- [x] `getUserById` реализован через Prisma
- [x] Unit-тесты для `AuthService` (>80% покрытия) — 100% по всем метрикам

## Как мы это делали

**gRPC-сервер на 5001 и `ValidateToken`** — это было готово ещё до начала работы
(скелет сервиса). Реально завелось не сразу — по пути поймали пару инфраструктурных
багов, о них ниже.

**`register`** — начали с того, что в `auth.proto` вообще не было метода `Register`,
только `ValidateToken`/`GetUserById`. Дописали RPC и сообщения. Решили, что в ответе
`register` будет возвращать не только токены, а ещё и данные юзера — чтобы фронту не
пришлось сразу после регистрации делать второй запрос за юзером. Сама логика простая:
проверяем, нет ли уже юзера с таким email (если есть — ошибка "уже существует"),
хешируем пароль через bcrypt, создаём юзера в базе через Prisma, генерируем пару
токенов и отдаём всё вместе.

**`login`** — по сути то же самое, только вместо создания юзера — поиск по email и
сверка пароля через `bcrypt.compare`. Тут словили реальный баг: сначала проверка пароля
шла раньше проверки "а нашёлся ли вообще юзер" — если юзера с таким email не было, код
падал с обычной ошибкой вместо аккуратного "неверные данные". Поправили порядок:
сначала проверяем, что юзер есть, и только потом сверяем пароль.

**Токены (access/refresh)** — обсуждали заранее, как их генерировать с разными
секретами и разным временем жизни (15 минут / 7 дней). Договорились, что дефолтная
настройка `JwtModule` — это конфиг под access-токен, а для refresh мы явно
переопределяем secret и время жизни прямо в вызове. Так минимум лишнего кода, и не
дублируется конфигурация. Плюс в refresh-токен решили класть по минимуму данных
(только id юзера), чтобы если он утечёт — вреда было меньше.

**`user.registered` в Kafka** — в проекте вообще не было ни одного Kafka-producer'а,
поэтому написали с нуля переиспользуемый сервис (в отдельном пакете `@shopflow/kafka`,
чтобы потом им же пользовались product/order/payment-service). Обсуждали отдельно
вопрос — что делать, если Kafka в момент регистрации недоступна: решили не ронять
регистрацию из-за этого, юзер уже создан в базе, это главное, а событие в Kafka просто
залогируем как ошибку, если не получилось отправить.

**`getUserById`** — раньше была просто заглушка с "not implemented". Заменили на
обычный запрос в Prisma по id, с ошибкой "не найден", если такого юзера нет.

**Юнит-тесты** — написали `auth.service.spec.ts` на все четыре метода (`register`,
`login`, `getUserById`, `validateToken`). В проекте вообще не было Jest-конфига (это
первый тест-файл в репозитории), пришлось сначала добавить `"jest"`-блок в
`package.json` сервиса. Мокали всё, с чем `AuthService` общается снаружи: `Prisma`
(`findUnique`/`create`), `TokenService`, `KafkaProducerService` и сам `bcryptjs` —
никаких реальных БД/сети в тестах. Отдельно проверили и пограничные случаи, которые
раньше ловили как баги: что `login` не падает, а возвращает аккуратную ошибку и на
несуществующий email, и на юзера вообще без пароля (OAuth-only), и что сбой Kafka
не валит регистрацию целиком. Покрытие — 100% по строкам и по веткам.

## Что ещё всплыло по дороге (не баги в логике, а инфраструктура)

Когда дошло до реального запуска сервиса, вылезло несколько вещей, которые
компилятор не ловит, а падает только при живом старте:

- В `app.module.ts` забыли подключить `PrismaModule` и `KafkaModule` — сервисы
  инжектились в конструктор, но нигде не были зарегистрированы, поэтому Nest не мог
  их найти при старте.
- В `main.ts` был неверный путь до `.proto`-файла (лишний уровень `../`) — сервис не
  находил контракт.
- Новая версия Prisma по умолчанию генерирует клиент в другом формате модулей (ESM),
  а весь бэкенд написан в старом (CommonJS) — из-за этого падало с непонятной ошибкой
  при старте. Нашли у Prisma отдельную настройку, которая переключает формат — и всё
  завелось.
- В `.env` секреты для JWT ещё были плейсхолдерами короче 32 символов — их и должна
  была отловить наша валидация, и она отловила, просто нужно было вписать нормальные
  значения.

## Как это проверить

Юнит-тесты (без поднятой инфраструктуры, всё замокано):

```bash
npm run test --workspace=@shopflow/auth-service
```

Живой сквозной прогон — поднять инфраструктуру и сам сервис:

```bash
docker compose up -d postgres kafka zookeeper
npx turbo run dev --filter=@shopflow/auth-service
# в логе должна появиться строка: "Auth Service gRPC listening on port 5001"
```

Дальше дергать gRPC-методы напрямую — через `grpcurl` (`brew install grpcurl`) или
через Postman (там тоже есть gRPC-запросы, но нужно вручную указать `.proto`-файл,
Postman сам его найти не сможет):

```bash
grpcurl -plaintext \
  -import-path packages/proto/proto -proto auth.proto \
  -d '{"email":"test@shopflow.dev","password":"Test1234!","name":"Denis"}' \
  localhost:5001 auth.AuthService/Register
```

Сценарии, которые стоит прогнать руками:
- `Register` с новым email → должны прийти `user` + токены.
- `Register` повторно с тем же email → ошибка "уже существует".
- `Login` с правильным паролем → `user` + токены.
- `Login` с неверным паролем или несуществующим email → аккуратная ошибка
  "неверные данные", а не падение сервиса.
- `GetUserById` с id из ответа `Register` → тот же юзер.
- Событие в Kafka можно посмотреть в Kafka UI (`localhost:8080`, топик
  `user.registered`) или прямо из терминала:
  ```bash
  docker compose exec kafka kafka-console-consumer \
    --bootstrap-server localhost:9092 --topic user.registered --from-beginning
  ```

## Темы, которые затрагивались (для памяти)

- **NestJS `JwtModule`**: `register()` vs `registerAsync()`, как резолвится
  `secret`/`expiresIn` при явном override в `signAsync()` (merge, не замена).
- **`@nestjs/config`**: `validate` vs `validationSchema` (Joi-специфичный),
  откуда `ConfigService.get()` реально берёт значения (`getFromValidatedEnv` →
  `getFromProcessEnv` → `getFromInternalConfig`).
- **gRPC error model**: стандартные коды `Status` из `@grpc/grpc-js`, `RpcException`.
- **Proto3**: уникальность номеров полей, зачем RPC обязательно объявлять в
  `service {}` блоке отдельно от message-типов.
- **Kafka базовые концепты**: broker/topic/producer/consumer, at-least-once и
  log-and-continue vs outbox pattern.
- **Prisma 7 генератор `prisma-client`**: ESM vs CJS вывод, `moduleFormat`.
- **npm workspaces**: где ставить зависимости (только из корня), хойстинг и
  фантомные зависимости.
